# ADR-001: Replay-Safe Execution Gateway for Synthetic Agent Actions Using Transactional PostgreSQL Idempotency

**Date:** 2026-10-15
**Status:** Accepted for scoped demonstration; documented boundaries for production.
**Deciders:** Lead Software Engineer & Reliability Architect

---

## 1. Context and Problem Statement

When autonomous AI agents or orchestration frameworks invoke side-effecting tools (such as publishing updates, creating tickets, or making purchases), network timeouts, lost HTTP responses, or LLM retry loops frequently cause the agent to replay the same logical request.

In the unmitigated baseline, every incoming delivery executes the synthetic action anew, creating duplicate side effects. In real operations, duplicate effects degrade user trust, create operational cleanup costs, and risk duplicate financial charges or customer communications.

We require an architectural pattern for the `POST /v1/actions` endpoint (`publish_update` action) that guarantees:
1. Exact request replays execute the underlying effect exactly once and return the stored canonical result.
2. Concurrent duplicate requests do not race into duplicate effects.
3. Key reuse with modified payload content is rejected with HTTP 409 Conflict.
4. Database failures roll back the entire transaction atomically.

---

## 2. Options Considered

### Option 1: In-Memory Deduplication (Process Cache / Set)
Maintain a dictionary or LRU cache of processed `idempotency_key`s in the application runtime memory.

- **Pros:** Zero database overhead; microsecond lookup latency.
- **Cons:**
  - Cache is lost immediately on application restart, crash, or deployment.
  - Does not share state across multiple worker processes or containers.
  - High memory footprint as action volume scales.
- **Verdict:** **Rejected.** Inadequate for persistence across crashes or multi-worker architectures.

### Option 2: Naive Check-Then-Act Pattern (`SELECT` then `INSERT`)
Query the database (`SELECT ... WHERE idempotency_key = %s`); if no record is found, execute the effect and insert the record.

- **Pros:** Simple to understand and implement without advanced SQL primitives.
- **Cons:**
  - **Severe race condition:** Two concurrent requests can both execute the `SELECT`, both observe "key not found", and both proceed to execute duplicate effects before either commits.
  - Relies on application-level coordination rather than database-enforced atomicity.
  - Prone to partial failure if effect creation succeeds but record insertion fails.
- **Verdict:** **Rejected.** Concurrency failure mode is catastrophic for idempotency.

### Option 3: PostgreSQL Uniqueness + Single Atomic Transaction (Chosen)
Utilize PostgreSQL database-level uniqueness constraints on `actions(idempotency_key)` and `effects(idempotency_key)`, executing the key claim, synthetic effect creation, and stored result finalization within a single atomic transaction. Concurrency is resolved using `INSERT INTO actions ... ON CONFLICT (idempotency_key) DO NOTHING` paired with row locking (`FOR UPDATE`).

- **Pros:**
  - Guaranteed atomicity: either both action record and effect commit, or neither does.
  - Concurrency safety: PostgreSQL enforces unique index locking, serializing concurrent attempts on the same key without table locks.
  - Conflict detection: compares SHA-256 payload hash against the stored hash and returns HTTP 409 if tampered.
  - Portable across all PostgreSQL-compatible environments (local Docker, RDS, Cloud SQL).
- **Cons:**
  - Holds row locks during the transaction; requires transactions to remain short.
  - Only covers side effects whose state resides within the same PostgreSQL database.
- **Verdict:** **Chosen** for this scoped demonstration.

### Option 4: Transactional Outbox + Provider-Side Idempotency
For workflows where side effects involve external network services (e.g. Stripe, SendGrid, external APIs), write an "outbox" intent row into PostgreSQL within the transaction, and have a reliable background worker deliver the call using provider-level idempotency headers.

- **Pros:** The only sound pattern for guaranteeing at-least-once external delivery with receiver-side deduplication.
- **Cons:** Requires message broker/queuing infrastructure, worker processes, dead-letter queues, and reconciliation loops, which exceeds the single-flow synthetic demonstration scope.
- **Verdict:** **Deferred to production roadmap;** documented as the mandatory next step when external side effects are introduced.

---

## 3. Decision Outcome

We chose **Option 3 (PostgreSQL Uniqueness + Single Atomic Transaction)** for the RelayGuard service.

### Technical Implementation:
1. **Schema:**
   - `actions`: `idempotency_key TEXT PRIMARY KEY`, `payload_hash TEXT NOT NULL`, `result_json JSONB NOT NULL`, `created_at TIMESTAMPTZ`.
   - `effects`: `effect_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `idempotency_key TEXT NOT NULL UNIQUE REFERENCES actions(idempotency_key)`.
2. **Transaction Sequence:**
   - Execute `INSERT INTO actions (idempotency_key, payload_hash, result_json) VALUES (%s, %s, '{}'::jsonb) ON CONFLICT (idempotency_key) DO NOTHING`.
   - If row was not inserted (`rowcount == 0`), lock existing row (`FOR UPDATE`), compare payload hash. If matching, return cached result with `replayed: true`; if mismatch, raise HTTP 409.
   - If row was inserted (`rowcount == 1`), insert synthetic effect into `effects`, compute canonical response, update `actions.result_json`, and commit.
3. **Database-level Rollback:**
   - If any step fails (e.g. database error, injected trigger fault), `connection.transaction()` automatically triggers `ROLLBACK`, leaving zero orphan rows.

---

## 4. Consequences and Trade-offs

- **User & Agent Experience:** Replays return fast, deterministic cached responses. Transient retries do not trigger duplicate operations.
- **Maintainability:** Minimal codebase, no extra queuing dependencies (Celery, Redis), strictly typed Pydantic models.
- **Operating-Cost Exposure:** Repeated tool calls do not consume downstream database writes or processing capacity.
- **Honest Boundary Limitation:** This pattern guarantees exactly-once effect creation *because the effect is synthetic and stored in the same database*. It does **not** provide a magic distributed exactly-once guarantee for external third-party HTTP calls.

---

## 5. When to Revisit

Revisit this decision when:
1. Real external third-party APIs (payment processors, email gateways, SaaS webhooks) are integrated $\rightarrow$ Adopt **Option 4 (Transactional Outbox + Provider Idempotency)**.
2. Request volume exceeds single-database write throughput $\rightarrow$ Introduce Redis distributed leases or distributed database sharding.
3. Action history retention requires archiving $\rightarrow$ Implement automated TTL partition pruning for keys older than 30 days.
